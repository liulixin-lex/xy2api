# 用“份额调度”替换智能可控调度，并保留 Sub2API 原版调度

## 背景

运营中转站时，上游账号的流量分配既要避开故障账号（智能），又要保证首字速度与缓存命中（体验），还要让管理员设定的优先级和比例真正生效（可控）。当前两套调度都做不到三者兼顾：

- **Sub2API 原版**没有账号流量权重；实验调度器把优先级当软评分因子，备用账号空闲时也会拿到约 1/3 的首选流量；“低倍率优先”会压过优先级；粘性会话不随配置迁移。
- **智能可控调度（controlled）**虽然有严格层级与层内 SWRR，但在分配上叠加了健康状态机、容量溢出、恢复爬坡、重试账本、故障域等自动机制，分配计数器随候选集合切换，完全没有会话亲和；每个请求都要多次访问 PostgreSQL，且模式读取失败会让所有网关请求返回 503；改动侵入 65 个非测试文件和整条上游 HTTP 链路，反复重写，维护与上游同步成本很高。
- 两者都不给出“某账号为什么少拿了流量”的可追溯原因。

详细分析、外部项目对比与仿真见 [`docs/SCHEDULING_ANALYSIS.md`](../../../docs/SCHEDULING_ANALYSIS.md) 与 [`simulation/RESULTS.md`](simulation/RESULTS.md)。2026-10-10 按“不降低缓存命中率与首字延迟”修订了亲和、溢出与回升规则，依据见 RESULTS 第二部分。

## 变更内容

1. **保留 Sub2API 原版调度**（调度器键 `sub2api`）：算法、设置与界面回到上游 v0.2.14/0.2.15 的形态，作为默认调度器和一键回退目标；与上游的差异只剩现有通用二开（IQ 门控、组合分组、Codex Ticket 等）和一个调度器分发钩子。
2. **完全剔除智能可控调度**：删除 `backend/internal/scheduling` 包、全部 controlled 服务适配、请求中间件、上游 HTTP 包装、handler 中的 controlled 分支、管理接口、前端页面/状态/文案、CI 门禁与同步策略条目；网关热路径不再为调度读取数据库。已发布迁移不改写，历史表保留一个版本作回滚缓冲，之后再以新迁移清理。
3. **新增份额调度**（调度器键 `share`，按分组开启）：
   - 管理员为每个分组设置**层级（tier）+ 权重（weight）+ 排空（drain）**，这是唯一的流量意图来源；
   - 层级严格优先；层内**新会话**按加权会话一致性哈希（HRW）分配，份额与权重严格成比例，账号进出只迁移最少的会话；
   - **缓存优先的会话亲和**：
     - 亲和键跨轮稳定；
     - 绑定账号满载时按缓存价值有界等待，超时溢出并改绑，缓存随会话走；
     - 短时不可用只软溢出；
     - 改权重、回升、排空只在会话缓存变冷时迁移，管理员显式设置的截止时间除外。
     - 仿真中缓存命中率与原版持平，TTFT P95/P99 低于原版；
   - 自动机制只做两件事：复用原版资格闸门**排除**不可用账号；可选的有界纠偏只在管理员设定区间内**缩放新会话权重**；
   - 每次偏离理想选择都记录原因码，提供“目标 vs 实际 vs 原因”报表、单请求解释（Explain）与改配置前的份额预览；
   - 热路径零新增数据库查询，选择阶段 Redis 往返不多于原版；配置读取失败时使用最后已知配置，冷启动无配置时回落原版调度，不返回 503；
   - 缓存归因（原版与份额分组同口径）、影子运行与灰度门禁，用数据证明“缓存命中与首字不退化”。

## 影响面

| 范围 | 影响 |
|---|---|
| 后端 | 删除约 6.0k 行核心 + 4.9k 行适配 + 1.2k 行管理接口及对应测试；新增 `internal/sharesched`（纯算法）与少量服务适配、管理接口 |
| 数据库 | 新增 `share_scheduling_policies` 迁移，导入旧分组策略为“未启用草稿”；controlled 历史表保留（只读、无代码引用），后续版本再删除 |
| API | `/api/v1/admin/scheduling/*` 退役（一个版本返回 410 指引），新增 `/api/v1/admin/share-scheduling/*` |
| 前端 | 删除可控调度页面与模式切换组件，恢复原版设置/账号列；新增分组份额配置、报表与解释页面 |
| 计费 | 计费意图中的 `SchedulingAttemptID` 保留为兼容字段并忽略，耐久计费（迁移 267）路径不变 |
| 观测 | 新增缓存归因与选择耗时，原版分组同样采集（只读观察，不改变选择）；新增 Redis 统计键，失败只丢统计 |
| CI / 同步 | 替换“Scheduling reliability”门禁；移除 `typesafe-controlled-settlement` 补丁或改挂到原版路径测试；上游同步冲突面显著缩小 |
| 升级行为 | 所有分组落到 `sub2api`；管理员审阅导入的草稿后按分组启用份额调度 |

## 非目标

- 不改变原版 Sub2API 的选号、粘性、负载与故障转移逻辑。
- 不引入新的健康状态机、首输出预算账本或派发票据；故障转移沿用原版 handler 循环与账号冷却。
- 不做逐模型的层级/权重（列为后续可选项）；模型只用于能力筛选与原版模型路由。
- 不承诺消除重尾大会话造成的成本份额波动；需要硬封顶时使用账号窗口费用、额度阈值等现有硬闸门。
- 不迁移生产数据；未经用户另行授权不推送、不发版、不部署。

## 已定稿的决策

2026-10-10 用户授权按当前代码与方案全权决策 D5、D8、D9、D10 并开始开发；D1–D10 均按下表定稿实施。

| 编号 | 问题 | 决定 |
|---|---|---|
| D1 | 升级时原 controlled 用户落到哪里 | 全部落 `sub2api`，旧分组策略导入为未启用草稿，由管理员逐组启用 |
| D2 | 新调度器名称 | “份额调度”（`share`）；可改 |
| D3 | OpenAI 质量路由（当前两种模式下实际都未生效） | 原版保持不启用；份额调度中作为可选显式闸门，二期再定 |
| D4 | Codex 429 压力自适应并发（当前仅 controlled 生效） | 份额调度中作为显式容量闸门保留并在解释中可见；原版不启用 |
| D5 | 层级回升默认策略 | `cold`：高层稳定 120 秒后，低层会话在各自缓存变冷时迁回；不设强制截止。需要严格回升的分组显式设置截止时间，预览显示代价（仿真约 1 个百分点缓存命中）。替代 2026-10-09 建议的 `stable` |
| D6 | 份额统计单位与纠偏默认值 | 默认按新会话份额、不纠偏；可选请求数/Token/标准成本 + 温和纠偏 |
| D7 | controlled 历史表的删除时间 | 新版本后保留一个正式版本，再用独立迁移导出后删除 |
| D8 | 绑定账号满载时的行为 | 按缓存价值等待：默认 100ms/1k Token，上限 15 秒，排队 ≤3；超时溢出到会话 HRW 次选并改绑。原版是一律最多等 120 秒；初版是立即溢出、不改绑，仿真中缓存命中低 3–6 个百分点 |
| D9 | Anthropic 无会话标识客户端的亲和键 | 份额分组改用对话锚点（API Key + 系统/工具 + 首条用户消息）；原版分组保持原哈希。原版回退哈希在客户端移动缓存断点时逐轮变化，或让不同 Key 共用一个哈希 |
| D10 | 缓存归因是否覆盖原版分组 | 覆盖：只读观察、抽样 1/4 会话，先于份额调度上线以积累基线 |
