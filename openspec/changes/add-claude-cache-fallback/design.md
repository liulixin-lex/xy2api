## 1. 决策与范围

首版实现「缺失时补齐」，不实现「强制重写现有断点」。理由是现有实验证明合法声明可以透传并执行，而实际低命中请求缺少正文，不能假定已有声明都放错位置。

适用条件同时满足：原生 Messages 入站、实际账号为 `anthropic/apikey`、非显式 passthrough、最终仍使用 Messages 协议、管理员策略命中、实际上游与映射后模型属于已验证范围。OAuth、SetupToken、Vertex/Bedrock 专用路径、Antigravity、Chat/Responses 转换与 count_tokens 暂不接入。后续新增路径须单独验证。

不以 `Go-http-client` 等 User-Agent 判断客户端，也不把同一个 NewAPI Key 下的所有客户端当作一个会话。

## 2. 当前代码事实

| 位置 | 已核对行为 | 对设计的约束 |
| --- | --- | --- |
| `backend/internal/service/gateway_forward.go` | OAuth mimicry 才调用旧消息断点改写；公共流程会清理非法/超量断点 | 不复用旧开关开启 API Key 补齐；在清理前记录原始声明是否存在 |
| `gateway_upstream_request.go::buildUpstreamRequest` | 处理地址、beta、分组 system 后创建 HTTP 请求，返回实际 wire body | 在最终 system 处理后、创建请求前执行新 helper |
| `gateway_messages_cache.go` | 旧改写先移除消息断点，再设置末尾位置和 TTL | 与本功能的保留策略不符，不直接调用 |
| `gateway_claude_oauth_body.go` | 1h 注入只改已有声明，且限 OAuth/SetupToken | 不把 TTL 注入等同于缺失补齐 |
| `gateway_upstream_response.go` | 提取流式/非流式缓存用量 | 保留原始上游分类，不按注入动作推定命中 |
| `gateway_usage_billing.go` | 持久结算前可能执行 ForceCacheBilling、TTL 计费覆写 | 补齐不得触发或绕过它们；诊断区分原始 usage 与结算 usage |
| `billing_service.go::computeCacheCreationCost` | 有总写入量、无 TTL 明细时按 5m 回退 | 不能据此证明上游实际没有收取 1h 费用 |
| `billing_inflight_reservation.go::estimateOne` | token 预留按普通输入价和输出价估算 | 自动写缓存的候选请求须考虑较高的冷写价格，不能按预期热读低价预留 |
| `setting_gateway_runtime.go` | 既有转发设置使用进程缓存，TTL 60 秒 | 明确多实例设置传播边界，不声称跨实例瞬时关闭 |

这些路径在当前基线上的正常行为已有诊断证据；新增实现仍需自己的回归，不能把先前未加功能时的测试当作新代码验收。

## 3. 配置模型

采用独立、强类型的系统设置 `claude_cache_fallback_policy`，存入现有 settings 表。首版不在 groups/api_keys 表分别增加开关，避免多个开关优先级及认证快照迁移。策略仅由管理员修改，不放进公共设置或页面公开初始化数据。

以下为计划中的契约示例，ID 和地址均为虚构值，不是现成可用的配置：

```json
{
  "enabled": false,
  "rules": [
    {
      "id": "pilot",
      "group_id": 101,
      "api_key_ids": [202],
      "account_id": 303,
      "base_url": "https://provider.example",
      "models": ["claude-opus-5-5"]
    }
  ]
}
```

- 未设置、读取失败、格式错误或 `enabled=false`：不补齐，继续既有转发。开启但规则为空也不扩大范围。
- 规则全部是允许规则，命中一条即可；没有隐式全局兜底。重叠规则不重复注入，诊断固定使用第一条命中的规则 ID。
- `api_key_ids=[]` 明确表示该分组全部 Key；非空时只匹配所列 Key。首轮灰度使用非空列表。不提供同时存在的允许/拒绝优先级。
- 每条规则明确分组、账号、规范化完整 base URL 和非空最终模型精确名单；首版不支持模型通配、任意上游或缺省账号。地址比较须保留 base path，不能只比 hostname。
- 保存时核验分组/Key/账号归属与类型、ID 唯一性、模型名单、URL 格式及总大小；上限建议 100 条规则、每条 100 个 Key 和 50 个模型，避免无界热路径扫描。沿用已有 URL 校验，不发网络探测。
- 实际执行时重新核对本次有效分组、所选账号、实际目标地址与映射后模型。规则不授予模型权限、不选路、不绕过限额。Key 换组、账号换地址或映射到未列模型后自动不命中。
- 保存沿用部分更新契约：省略该设置保留原值；明确提交关闭才关闭。修改其他设置不能误清空规则。
- 使用独立不可变运行快照，不借旧 OAuth 默认值。当前实例成功保存后刷新；其他实例最长 60 秒重新加载，过期后刷新失败返回关闭，不无限沿用旧的开启状态。已发送请求继续原有处理。
- 账号凭据、上游内部路由或提供商行为变化后，需要重新核验。一次通过不生成“永久支持”的推断；首版不增加自动付费探测任务。

## 4. 转发中的补齐规则

### 4.1 原始声明检测

在任何缓存净化/裁剪前，检测原始请求的协议位置：根 `cache_control`、`system[*].cache_control`、`tools[*].cache_control`、`messages[*].content[*].cache_control`。

任何这些位置出现字段都视为客户端已提供意图，包括 `null`、非法类型、thinking 上的非法字段或超过四个断点。新功能不替客户端纠错；既有校验、清理或错误行为保持。不得因为已有清理把字段移除后，就把请求误判为从未声明。

不递归扫描 tool 的 JSON schema、tool input 或文本内容中的同名字符串，它们不属于协议声明。检测结果仅存请求内存，不记录完整内容。

### 4.2 最终出站处理

在最终账号、地址、模型确定，并完成分组 system 注入等既有处理后：

1. 不在原生 Messages/API Key 白名单范围，或设置未开启：直接返回既有正文。
2. 原始请求已声明，或最终正文被其他合法步骤加入声明：直接返回既有正文。
3. 所有前提满足：仅在根增加 `"cache_control":{"type":"ephemeral"}`。不写 `ttl:"1h"`，不更改模型、内容、工具顺序、思考参数或会话标识。
4. 修改局限在本次构造的 wire body，不能把补齐后的正文写回原始共享请求体。既有重试/换号每次用当前账号重新判断，防止对 A 的声明泄漏到未验证的 B。

使用现有 JSON 字节处理方式进行局部插入；不得通过整棵 map 重编码改变其他字段。关闭或跳过时，相对现有处理流程的最终字节必须一致。无法可靠解析时不猜测注入，交既有请求校验处理。

顶层自动缓存的具体断点由上游选择，因此首版不另写“最后一条消息一定可缓存”的算法。短请求可能不满足模型阈值，零写入/读取本身不证明上游不支持。前缀变化、TTL 到期、超过回溯窗口或并发冷启动也不能靠补字段保证命中。

### 4.3 重试和错误

补齐功能本身不增加任何上游调用。遇到不支持参数的 400/422，仅记录兼容性诊断并进入既有错误处理；不自动删字段再重放，不升级 TTL，不据单次零命中更换账号。既有调度的预算、已输出内容禁止重放和取消规则保持。

管理员关闭规则后恢复缺失请求的原行为；客户端本来带的声明继续按原流程处理。关闭不是删除上游缓存，也不撤销已发生的写入费用。

## 5. 上游兼容性验收

能力范围是「实际上游地址 + 账号 + 最终模型 + 协议」，不能仅按模型以 `claude-` 开头判断。自动启用未知上游、直接套用 OAuth 改写、运行时猜测兼容性均不采用。

每个拟开启的组合，先在隔离环境完成 mock 验证，再在已有授权和明确费用预算内进行受控合成探测：

| 情形 | 验收依据 |
| --- | --- |
| 全新稳定前缀 + 顶层默认 TTL | 完整成功响应，缓存写入 > 0，5m 明细与总量一致 |
| TTL 内重复相同正文 | 读取 > 0，普通输入显著下降；受控长前缀目标命中率 ≥ 95% |
| 追加对话 | 旧前缀可读取、新增部分正常处理，正文语义不变 |
| 已预热内容但不开补齐 | 按实际基线记录，不预设所有上游都一定零命中 |
| 兼容端点接受字段但始终无读写 | 不能以 HTTP 200 标为支持，保持未启用并调查 |
| TTL 明细缺失、相互矛盾或实际按 1h 写入 | 不判为计费验收通过，停止扩大启用范围 |

确认的当前样本为全新前缀 11,409 写入 → 11,409 读取，仅覆盖当时那一个账号/模型。上线前应复用本地证据选择测试范围，不无意义重复收费；账号、地址或相关实现发生变化才重新验证。

## 6. 计费契约

仅添加缓存声明不代表获得了缓存命中，不得根据请求字段重新分配 token。

正常文本费用按独立类别计算：普通输入 + 5m 写入 + 1h 写入 + 缓存读取 + 输出，再应用既有定价、长上下文规则和倍率。`cache_creation_input_tokens` 是写入总数，5m/1h 是细分，不能把总数和细分重复收费；Anthropic 普通 `input_tokens` 不包含缓存读写。

- 使用上游实际返回分类，包括上游报告的混合 TTL；不能因为本功能发了默认 5m，就把所有写入强改为 5m。
- 流式 message_start/message_delta 的既有合并不得清零前期用量或重复累加；非流式、部分流和取消继续走现有结算。
- ForceCacheBilling 和 TTL 计费覆写属于既有商业策略。本功能不主动开启它们；记录原始用量与最终账单的差异原因。首轮灰度选择未配置这些覆写的账号。
- 当前无 TTL 明细时回退 5m 的分支是已有计费边界。首版不在缓存功能中顺手重写所有计费规则；对缺失/矛盾明细发出限频诊断，验收不能凭请求 TTL 推定真实供应商费用。需要修正该边界时单独提交计费修复及回归。
- 5m 写入通常贵于普通输入，1h 更贵；重复使用才可能节省。管理端提示费用变化，不能宣传保证降费。
- 现有耐久结算意图、余额/额度扣除、重试幂等和删除 Key 后结算契约保持；缓存命中不绕过任何扣费步骤。

**在途预留必须一起核对。** 当前 `tokenInflightEstimate` 只传模型、body 字节数和输出上限，估算器使用普通输入价。首版需要为原始无声明且可能命中已启用规则的请求传递内部缓存冷写估算标记：输入侧按实际定价配置中普通输入价与 5m 写入价的较高者预留，仍计输出上限与既有倍率，不能把 1.25 固定写死在账务逻辑，也不能假设会热读而少预留。账号尚未选择时使用候选范围的保守估算；若最终没有注入，暂占仍按既有生命周期释放，绝不把预留额直接当作费用扣除。重试、配置变化、取消和 Key 删除时不重复预留或泄漏句柄。

字节估算与 token 上限原本就不是精确 tokenizer，调整价格项不构成“绝不透支”的保证；需用低余额并发、冷写贵于普通输入、自定义价格和不匹配账号对照检验新增影响。订阅模式沿用现有预留/配额边界，不因本功能另行改成余额模式。

对账分三端：上游商向 XY2API 收费、XY2API 向调用 Key 收费、NewAPI 向其客户端收费。现有 15 个样本只证明响应用量与 XY2API 账单一致，没有上游商或对方 NewAPI 的账本，不能保证另外两端。

## 7. 诊断与管理界面

新增结构化事件建议为 `gateway.claude_cache_fallback`，包含 request_id、规则 ID、有效分组/Key/账号 ID、最终模型、`injected/skipped` 和固定原因码。原因码至少覆盖 disabled、scope_mismatch、unsupported_route、client_declared、final_declared、injected、invalid_body。

在响应结束时关联上游普通输入、写入/读取、TTL 细分、已有计费覆写标记及 usage 记录 ID。不记录 Authorization、API Key 文本、邮箱、prompt 正文、tool arguments 或任意原始错误正文。缓存字段值只输出预定义类型/TTL 枚举，不把畸形字段内容原样打日志。

首版不保存 prompt 哈希、不建设跨请求会话追踪服务，不把 Key 当作会话。若后续排查前缀变化，需要另行限定采样范围、周期与隐私处理。监控指标不使用请求 ID/Key 作为高基数标签。

管理端使用现有设置页中的独立组件：开关、规则列表、分组选择、可选 Key 多选、该组账号、地址只读核对、模型精确名单。展示「首次写入可能增加费用；仅对已验证的上游启用」和「配置在其他实例最长约 60 秒生效」。保存不触发付费探测。普通客户端不需要修改代码。

## 9. 实施阶段与发布门槛

1. **配置与纯函数**：默认关闭、严格作用域、声明保护、幂等、大小边界。
2. **真实转发出口与诊断**：受控 HTTP 上游验证 wire body、SSE/JSON、重试换号和真实计费分类。
3. **管理设置与回归**：旧客户端省略字段兼容、跨实例 60 秒传播、权限和错误反馈。
4. **验收后灰度**：只选一个已验证账号/模型和一个调用 Key，核对完整冷写/热读/追加对话及费用，再考虑扩大范围。

离线验收必须覆盖全部规格场景；实现涉及的 Go 单元/集成、设置前端类型/测试/构建、并发快照 race 和仓库既有 CI 门禁均通过。实际调用数不得因补齐增加；费用分项按既有数据库精度逐项一致。

2.65 MB 合成正文纳入性能回归，报告与关闭状态的 CPU/分配差值；不得增加每请求 SQL 查询、网络能力探测或无界正文副本。性能结论由测量给出，不预先承诺百分比。

灰度先看错误率、write/read token、每轮总费用及原始/结算用量差异，不能只追求命中率。参数错误或账单异常立即停用对应规则，记录已产生费用；跨实例关闭按既定传播窗口验收。未知真实低命中根因、未取得两端账本、未覆盖全部上游是明确限制。

## 10. 后续候选

块级兜底、覆盖已有早期断点的增强策略、1h 选择、Chat/Responses 转换路径和前缀稳定性诊断均独立评估。没有客户端缺失声明的证据时，不能用第一版补齐代替它们，也不把这些后续功能视为本次已经授权实施。

## 实施补充（2026-10-08）

- 请求入口冻结 admission 快照，最终发送再次读取当前开关及匹配规则；在途启用不能让没有预留冷写成本的请求新增补齐。分组 fallback 不进入新组规则。
- Forward 成功同步 wire body 时移除本次自动插入的顶层字段，保留其他既有转换，避免部分流失败后的换号泄漏。
- 开关关闭或入口组/Key 不在范围时不扫描原始大正文；配置快照支持并发读取。
- 使用独立管理组件的局部保存，避免主设置页的旧快照覆盖缓存规则。
- 使用说明及计费边界见 `docs/CLAUDE_CACHE_FALLBACK.md`；灰度开启属于部署后的独立操作。
