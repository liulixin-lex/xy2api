# 稳定质量监测详细设计

本文是未来实现契约。当前分支 `fix/iq-response-protocol` 上的业务实现保持原样，本轮只增加本目录和项目记忆。

## 1. 证据与目标

AA26-251A官方PDF确实包含针对恶意蒸馏的响应调整建议；它没有公开OpenAI的生产判断逻辑，也没有证明本项目糖果题、JSON格式或定时器触发了该机制。社区反馈支持“存在质量体验差异”，不能替代对本项目错误路径的诊断。来源和日期见[sources.md](sources.md)。

优化目标是合法、低负载、可解释的质量监测。成功标准为减少重复和无效请求、遵守服务方限制、保持同一完整答案的确定性判分，以及让操作者分辨答案错误、传输异常和任务尚未执行。不能把“未收到封禁”或“答对了21”作为没有被服务方误分类的证明。

不提供反检测配置，不伪造真实用户行为，不添加闲聊来掩盖探测目的，不去除追踪标识来规避监测，不为受限请求轮换身份/代理/模型。协议兼容与真实应用身份配置属于正常工程工作，不能将代码中关于上游降载策略的历史注释当作已证实事实。

## 3. 请求规范与评分不变量

### 3.1 按端点构建请求

引入纯函数请求配置解析，例如`ResolveIQRequestProfile(account)`，返回认证类型、最终端点、Responses或Chat Completions、模型原始ID、思考深度、输出模式与传输类型。它不执行上游请求，不自动改账号配置。

- API key：采用端点文档要求的认证和普通API头；自有应用User-Agent真实标明XY2API及版本。默认不添加Codex专用originator、version、窗口身份。第三方确需额外头时必须是显式端点配置并经过适配验收，不添加“防检测头”选项。
- OAuth/Setup Token：核对现有授权接入方式和协议所需字段，复用兼容适配器，记录所用配置版本。模型文档支持Responses不代表任何内部OAuth端点均支持同一功能；未确认的能力按未知处理。遇到权限限制，不借换身份恢复探测。
- 账号配置变更使旧任务失效；正常令牌续期沿用原revision规则。OAuth与API key不共享质量结论，官方API测通也不能证明订阅OAuth必然正常。
- 可追踪request ID保留；客户端关联ID只用于诊断，不冒充人类或改变服务方身份判断。移除会话续接字段仅用于满足独立测试，不作为隐藏活动措施。
- 新配置通过一次明确的管理员动作启用；不在每轮开始前自动拉模型清单。模型列表沿用现有只读缓存。

### 3.2 固定题目与比较条件

保持原糖果题数学内容、数字和表格、candy-v2提示及candy-grader-v2规则。单次完整最终答案：

| 最终证据 | assessment.status | IQ限制 |
| --- | --- | --- |
| 明确答案21，JSON/纯数字/无歧义解释 | smart | 解除自身限制 |
| 明确其他数值，包括29 | degraded | 添加自身限制 |
| 无答案、歧义、拒答、流不完整、超时、HTTP/协议错误 | unknown | 解除自身限制 |
| 本次只是排队、预算不足、账号忙而未发请求 | 不产生新assessment | 保持上一评分决定 |

`IQCheck.BlocksScheduling()`仍等价于`enabled && status == "degraded"`。人工停用、过期、余额、限流等原有规则独立有效。关闭检测立即解除自身限制。调度不增加凭空计算的“上游蒸馏标签”。

不为了降低可识别性轮换题目、拼接普通用户内容或改答案。固定题目容易失去对整体能力的代表性，这是测量范围限制；本期界面说明“聪明/降智为本题通过/未通过”，不改变用户已选标签。

模型默认仍为`gpt-6-astra`/`low`，用户已有自定义设置保持；`upstream_default`仍表示省略参数。快照模型只有在上游实际提供可用ID时才可选，不能杜撰日期ID。请求的模型与reported_model同时保存，后者只是上游声明，不能当作真实内部路由的认证。

JSON是正规的机器可判分格式，继续默认compat并允许显式strict；Schema只约束整数，不包含21示例、const或enum。严格JSON不能保证内容正确。无需输出思维链，不请求推理文本、logprobs、系统提示或训练数据。

### 3.3 时间与生成预算

保留现有120秒默认，计划允许每个检测配置设置30～300秒总超时，所有取消/超时都为未知。新超时为比较配置的一部分，变更需失效旧任务；工作租约按总超时加60秒或心跳续租，避免高深度任务尚在运行就重复领取。

可见答案仍要求简短。初期不增加过小的max_output_tokens/max_completion_tokens；内部推理也可能消耗该预算。未来如提供token上限，默认省略，必须经所选模型/深度完成率验证；达到上限一律未知，不判降智。每轮的输入/输出/推理token数量（如上游提供）用于成本与预算解释，不凭“思考短”“token少”判降智。

## 4. 排期、预算与并发

### 4.1 向后兼容的配置

在`IQCheckSettings`中拟增`scheduling_mode=fixed|adaptive`、`max_interval_minutes`、`daily_request_limit`、`timeout_seconds`。旧客户端省略字段就保留。旧账号缺字段时默认为fixed、现有间隔、120秒；每日预算默认`ceil(1440 / interval_minutes)`，故15分钟为96，原来显式配置1分钟的账号不被静默改为15分钟。预算首次显式保存后独立于间隔，不随编辑间隔悄悄改变。

全局设置另有可配置IQ并发上限（建议2，硬上限沿用10）、共享配额组每日预算与执行速率。建议值是本项目资源管理初值，不宣称是服务方安全阈值。既有实例启用新限制前展示排期影响，所有账号合计请求量不能靠创建更多IQ任务突破所配置预算。

每日计数以UTC日为明确边界，标明重置时间；同时始终执行按账号最小间隔和共享上游实际RPM/TPM限制，避免午夜重置集中请求。计数只记真实尝试，手动、定时、配置触发共用；失败、超时及无法确认是否送达的请求也计数。不将数据库轮询当作上游请求。

### 4.2 固定模式与可选节约模式

fixed保留`interval_minutes`，在已完成轮次后计算下一次到期。adaptive是显式选择的节约探测模式：

- 首次或配置变更后尽快排队，预算和业务优先级仍有效。
- 连续3次可判分且smart，后续有效间隔从I变为2I；连续6次smart变为4I，上限为max(I,用户max_interval_minutes)，默认建议60分钟。
- degraded立即按单次规则限制账号，smart连续计数归零，下次按基础I继续恢复检测；不在同轮复测、提高深度或换模型直到通过。
- 真正unknown清空smart连续计数，按原因处理下一次到期；未发送而延期既不增加也不清空连续计数。
- 只变更频率/预算/模式不覆盖已完成评分；变更模型/深度/格式/超时等比较配置让旧任务失效并按现有配置变化规则进入未知等待。

在I=15、上限60、已稳定的阶段，全天理论请求从96降至24轮/账号，约减少75%；包括首次验证和异常时不是这个数字。均匀时点发生且持续到下一轮的变化，在没有拥塞时平均发现等待约从7.5变为30分钟，最长排期等待从15变为60分钟，再加扫描、队列、抖动与实际请求耗时。不能同时承诺75%请求降低且仍具有15分钟发现时效。间歇错误即使固定模式也可能漏测。

业务成功只能证明本次请求完成，不能免除到期糖果题，也不能给账号补“聪明”。本期不复制或重放业务正文进行质量评估。

### 4.3 领取、开始、完成分离

保留现有数据库跨实例锁与revision/lease_token机制，新增pending任务元数据：每账号最多一条待执行意图，不含对话正文。流程为：

`排期/手动触发 → 合并pending → 校验预算与冷却 → 尝试业务并发名额 → 再校验revision → 记账并开始轮次 → 一次上游尝试 → 判分和完成事务`

- 通过`ConcurrencyService.AcquireAccountSlot`原子占用真实账号名额，IQ还受自己的全局及同账号互斥限制。不能先读并发数再不加锁发请求。账号无并发上限时仍执行IQ自身限额。
- 账号忙时低优先级延期，不占业务等待队列、不抢先结束业务。只通过实际原子名额承诺总并发上限；当前已有业务时默认优先延期，但不声称完全禁止不同请求类型的任何时间重叠。
- 本地可用性门禁复用人工禁用、明确过期/配额恢复时间等健康信息，唯独不因IQ降智禁用而永不再测。不能直接调用含IQ条件的`IsSchedulable`筛掉恢复探测。
- 未发送的延期不创建新轮次、不消耗两轮正文保留名额；新开始轮次与清理最旧记录同事务。预算预留若进程在送达状态不明时退出，保守计为已尝试；能够证明尚未发送的预留才释放。
- 不在持有数据库事务锁时等待网络/Redis。账号名额、IQ租约与预算预留失败时有明确释放顺序；DB与Redis短故障导致延期，不能超额放行。
- 180秒固定租约随timeout_seconds扩展或续租；重启恢复只关闭已开始轮次为interrupted，未发送pending只恢复排期。旧revision结果不得写回。
- 队列公平按到期时间及账号ID，冷却账号不阻塞其他独立已授权账号；错误探测不迁移到另一个账号“补答”。有相同已知组织/项目配额的账号共用quota_group_id与冷却，不能按同域名推断所有独立客户同额度，也不能拆组来突破服务方限制。

### 4.4 手动动作与去重

`POST /accounts/:id/iq-check/run`返回结构化排期结果：pending/running/deferred、task_id、next_eligible_at、reason。重复点击复用任务。即使上轮已结束，手动检测也遵守基础最小间隔、日预算及服务方Retry-After；按钮显示预计时间。

首次开启、新配置都不能清零当日计数或绕过上游冷却。暂停后管理员恢复可排队，但不忽略仍有效的服务方限制。不要将“立即检测”解释为不受限地立即发请求。

## 5. 失败分类与恢复

HTTP失败先保留状态，再有界读取最多8KiB错误JSON，严格解析`error.type`/`error.code`及适用字段。不保存原始message、HTML、密码或响应片段。允许的错误码映射受版本控制，未知错误保持通用分类；HTTP状态本身不足以区分所有原因。SSE开始后的错误事件走相同规范化分类。

| 原因 | 本轮评分 | 后续动作 |
| --- | --- | --- |
| 完整正确/错误数值 | smart/degraded | 固定或adaptive正常排期，不同轮内重问 |
| 429临时限流、503临时过载 | unknown | Retry-After优先，无有效提示时延后；不立即重放 |
| 网络超时、5xx无明确永久原因 | unknown | 按基础I、2I、4I递增，最长max(I,60分钟)；正向少量抖动避免集中恢复 |
| 明确额度/计费不足 | unknown | 暂停自动探测，等待已知额度恢复时点或管理员恢复；没有恢复时点就不定期撞请求 |
| 刷新认证仍失败、明确权限/政策拒绝 | unknown | 暂停并显示处理建议，不更换身份或路径重试 |
| 明确模型/参数不支持 | unknown | 暂停至配置修改或管理员处理，不自动降低深度或换模型 |
| 协议/解压/损坏终态反复失败 | unknown | 延长排期；同配置连续3次后暂停自动任务，保留诊断供排障 |
| 内容拒答或答案歧义 | unknown | 正常基础I排期；不推断为政策限流，不反复诱导回答 |
| 本地繁忙/预算不足/已知健康冷却，尚未发送 | 保留旧assessment | execution=deferred，展示下一时点 |

Retry-After支持合法秒数和HTTP日期，转成绝对not_before；设为调度下限而非在工作线程sleep。超出本地最长等待策略时暂停/延期，不能截短后提前发。服务器时间偏差、过去时间、非数字或过大值有边界测试。共享配额明确时传播到该配额组。

本层每轮最多一次实际HTTP应用请求，不额外调用其他账号/模型。审计当前HTTPUpstream与插件的重试：若插件无法证明尝试数或提供控制契约，只允许人工验证并标记重试未知，不能宣称全链路exactly-once。接收过输出后不自动重放。TLS连接建立阶段的安全重连与已经送达的应用重试须区分，预算按可观察尝试保守记录。

## 6. 结果、任务和新鲜度

对外继续提供`iq_check.status`和已有筛选。新增只读`execution_state=idle|pending|running|deferred|paused`、`execution_reason`、`next_eligible_at`、`last_assessment_at`、`freshness=fresh|stale|never_checked`及每日剩余预算。内部独立保存assessment与execution，避免“暂停”被理解为降智。

- 开始检测不预先写smart；pending/running期间保留上次评分并标明时间。
- 新鲜度是结果年龄，超过期望间隔和允许调度延迟即stale；它不是新答案，不直接改`BlocksScheduling`。历史degraded不会仅因本地队列拥塞自动变smart/unknown；用户仍可通过关闭检测解除限制。
- 实际新轮次unknown仍按用户原规则解除IQ限制；这可能允许未知质量账号参与原调度，界面要可见。若将来需要“未知也禁用”，属于另一个明确政策，不在本期暗改。
- 同一账号下reported_model变动、模型配置变动与传输协议变动都分开记录。耗时/用量只是诊断，不是评分依据。
- 全列表筛选、分页总数、跨页选择仍以现有三态为准；execution筛选如增加必须在数据库分页前执行。cache/outbox同步评分、执行摘要及原有revision，不能只改界面。

正文只保留最近两轮，diagnostic仍受4KiB上限约束；新增预算计数和连续次数为有界数字，不是对话历史。日计数按账号/配额组聚合，保留当前UTC日及短暂跨日清理缓冲，删除账号清理其计数。保留上游request_id、配置版本、时间、协议及数字用量用于最近两轮支持材料；不保留更长全文轨迹，不采集真实业务提示。

`store:false`继续用于请求数据控制，不能在文案中表示它关闭上游监控。本地删除只约束本系统。

## 7. 界面与接口落点

编辑界面保持“间隔 / 模型 / 思考深度”顺序，下方新增检测排期：固定/节约，节约模式最大间隔，日预算，超时。旁边说明理论每日轮数及检测时效。旧值保留，批量编辑只更新勾选字段。

列表蓝色检测开关、绿色聪明/黄色降智/灰色未知保留；旁边显示最后检测时间和简短执行状态。暂停或stale有原因，不能用颜色造成“刚检测通过”的印象。检测记录继续用提取答案为主、原文和diagnostic折叠；新增“下载最近两轮诊断”，管理员手动提交给服务方。

沿用现有管理员API扩展字段，不改路径、不破坏旧响应字段；设置接口校验枚举和范围。新增支持材料下载只返回该管理员有权访问的指定账号最近两轮，脱敏端点路径/账号标识，绝不包含凭据。恢复暂停通过现有配置/排队接口明确定义，不隐式重置预算。

主要实施文件：

- `backend/internal/domain/iq_check.go`：配置、执行摘要和明确默认值。
- `backend/internal/service/iq_check_service.go`：预检/名额/执行调度，注入ConcurrencyService，配套Wire生成。
- `backend/internal/service/iq_check_request_profile.go`（拟新建）：端点请求配置解析；通用HTTP/插件传输审计只做必要改动。

## 8. 验证与实施顺序

阶段一先整合本地协议修复并验证测试/迁移；投产后使用最近两轮诊断确认真实失败阶段。没有生产失败样本时，不能将其根因定为反蒸馏。

阶段二实现规范请求、HTTP错误分类、共享并发、去重和预算，仍用固定间隔。先通过离线模拟和数据库集成，进行只观察的灰度验证：记录将做的限制操作，实际自动启闭按原已批准策略执行；不会为了评估额外发第二份请求。

阶段三开放显式adaptive设置和排期UI。每次请求只回答原糖果题；单次判分仍即时执行，连续smart只决定频率。不会为验收短时间连发大量问题。

验收指标：所有现有答案判分用例保持；故障从答案判分中正确分离；不突破账号/配额组预算与实际业务名额；旧任务不能覆盖；只保存两轮正文。15→60分钟稳定负载减少是虚拟时钟调度模型结果，真实账号表现与服务方误分类率无法在本地证明。

可选真实验收仅在另行授权后，对少量明确拥有授权的账号按实际支持协议观察正常一个周期；记录配置/请求ID/用量，出现明确拒绝即停止该账号自动探测并联系服务方。不得以对抗服务方分类器作为验收目标。

交付沿用四角色；方案阶段BASELINE/MODIFIED/ROLLBACK只验证文档新增与既有协议回放保持。将来实施再增加调度、并发、错误分类和迁移升级/回滚的实际证据；源码回滚脚本不操作生产数据库。
