# 设计

## 1. 现状与可复现问题

以当前源文件的副本执行判分审计，没有调用上游。脚本与字面输出位于 `/xy/artifacts/openai-iq-check/planning_parser_audit.py` 和 `planning-parser-audit.stdout`。

| 输入/操作 | 当前观察或代码行为 | 目标行为 |
| --- | --- | --- |
| `{"answer":21}` / `21` | 聪明 | 聪明 |
| `29` | 降智 | 降智 |
| `答案是21还是29，无法确定。` | 聪明 | 未知：答案不唯一 |
| `答案是21。有人认为最少需要29个，但这个说法不成立。` | 降智 | 聪明：明确答案为 21，后句是反例 |
| `{"answer":29,"answer":21}` | 聪明 | 未知：JSON 键重复 |
| `{"answer":21.0000000000000001}` | 聪明 | 降智：明确数值不等于 21 |
| `服务暂不可用，请稍后重试。` | 降智 | 未知：没有可用答案 |
| 只改 `interval_minutes` | `resetIQState` 重置结果与 revision | 保留当前结果及有效任务，只更新排期 |
| 新轮记录 | INSERT 依赖迁移 240 中的模型/题干默认值 | 显式保存本轮配置快照 |

上表前七项为实际程序输出；后两项为仓储代码审查发现，未来实施时补充集成回归。

## 2. 编辑表单与配置

桌面沿用当前表单样式，在检测开关下增加一排控件，顺序固定：

```text
智商检测  [开关]
检测间隔             检测模型                            思考深度
[15] 分钟            [gpt-6-astra，可输入/选择 ▾] [拉取]    [低 low ▾]
```

小屏按相同顺序纵向排列，模型名可显示完整，选择框支持键盘、加载/空列表/错误状态。关闭检测后允许预先配置，保存配置不会偷偷启动检测。

新增 `IQCheckSettings.model`、`reasoning_effort`、`output_mode`，示例：

```json
{
  "enabled": true,
  "interval_minutes": 15,
  "model": "gpt-6-astra",
  "reasoning_effort": "low",
  "output_mode": "compat"
}
```

- `model`：去除首尾空白后非空，最大 256 字节，禁止控制字符，保留大小写、斜杠和常见上游 ID 字符；不限制必须以 `gpt-` 开头。输入值就是发送给该上游的原始模型 ID，不经过业务模型映射或分组的模型/深度重写。
- `reasoning_effort`：默认 `low`。特殊值 `upstream_default` 表示省略推理参数，与发送 `none` 区分。其他值优先来自该模型声明，可包含新出现的上游档位；值限定为 1～32 个小写字母、数字、下划线或连字符，不接受任意 JSON。
- 有可信能力元数据时，展示支持档位及上游默认值；明确不支持推理的模型仅可选择 `upstream_default`。参考能力不作为强制阻断依据。缺少元数据时显示常见参考档位，可填写上游专用档位并标明支持情况未知。
- 切换模型后，原深度仍被支持时保留；被明确排除时标出冲突，要求在保存前选择有效档位，不静默切成较低深度。自定义未知模型不因缺少列表记录被禁止保存。
- 模型列表不表示实际调用一定成功。请求时不支持模型/深度、403、429 等都为未知，保留用户配置，不自动降低深度或切换模型。
- `output_mode`：`compat` 为默认，在高级设置内；`strict` 为显式选择。严格格式的支持取决于完整的账号、端点、协议和模型组合。
- 现有账号缺字段时补默认；已配置账号经列表开关、旧客户端或仅间隔编辑提交时，省略新字段表示保留。创建、更新、批量、DTO 与 TypeScript 类型共用默认化及校验语义，不能每次默认覆盖。
- 批量编辑可分别勾选修改模型和深度；不把某一账号的列表当作其他账号的支持列表。复制可保留所选检测参数，但检测关闭、状态未知、无历史；旧导入无参数采用默认，带参数导入校验后保留且仍关闭检测。

## 3. 账号模型发现

新增 `GET /api/v1/admin/accounts/:id/iq-check/models`，可用 `refresh=true` 刷新。复用 `upstream_models.go` 的请求构造、`fetchUpstreamModelList`、目录解析和既有认证/代理/TLS/插件传输，提取无账号写入副作用的公共函数。

不能直接复用以下管理动作作为检测模型选择器的数据契约：

- `GET .../:id/models` 在发现失败时可能返回默认模型或映射名称，OAuth 分支还会追加本地图片模型。
- `POST .../:id/models/sync-upstream` 会回退到配置模型、补充第三方注册表元数据，并可能通过 `UpdateExtra` 写入账号。
- `ModelWhitelistSelector.vue` 是多选且会合并白名单；IQ 模型应使用独立单选输入，复用外观和底层拉取函数即可。

新接口返回 `models`（ID、展示名、推理能力及逐字段来源）、`fetched_at`、`from_cache` 和安全错误摘要。上游直接返回的 ID 标记为 `upstream`；参考能力标记为 `reference`；空目录或拉取失败不能用默认列表伪装成功。已知仅图片、音频、嵌入用途的模型不作为推荐选项，手动输入仍由实际请求验证。

短缓存采用“账号 ID + 身份配置 revision + 请求协议/端点”作为键，TTL 5 分钟，同账号请求合并；失败可显示带时间的旧缓存并标记过期，否则保留当前输入和自定义入口。模型 ID/元数据缓存不包含检测对话。拉取不修改白名单、模型映射、检测状态，也不触发糖果题请求；正常 OAuth 刷新按原认证机制处理。

编辑尚未保存的凭据、端点或协议时，提示先保存这些变更再拉取，避免把旧账号配置的列表误当成新配置支持。关闭弹窗或切换账号时取消/忽略过期响应。模型发现针对指定管理员账号执行，不经过 IQ 调度候选筛选，因此降智停用账号仍可拉取模型。

## 4. 请求与结构化输出

保留糖果题的数学内容、数字和表格，仅统一末尾格式要求；升级题干版本为 `candy-v2`。外层与题干均要求“一个 JSON 对象，仅含整数 answer，不输出解释或 Markdown”。标准答案只在本地评分中存在，提示和 Schema 均不写 `21`，禁止 `const:21`、`enum:[21]` 或包含正确答案的示例。

共享 Schema：

```json
{
  "type": "object",
  "properties": {"answer": {"type": "integer"}},
  "required": ["answer"],
  "additionalProperties": false
}
```

| 上游协议 | 模型/深度 | 显式严格格式 |
| --- | --- | --- |
| Responses，包括既有 OAuth 路径 | `model`；非上游默认时 `reasoning.effort` | `text.format`，含 `type:json_schema`、`name`、`strict:true`、`schema` |
| Chat Completions | `model`；非上游默认时 `reasoning_effort` | `response_format.type=json_schema`，其 `json_schema` 内含 `name`、`strict:true`、`schema` |

兼容模式只发送统一文字要求；显式严格模式按上表添加参数。对不支持严格参数的上游记录未知及具体原因，不在同轮偷偷改参数重问。若上游忽略严格参数但返回完整纯数字 21，答案仍判聪明，同时记录 `format_compliant=false`，不把格式服从度等同于答题正确性。

每轮独立请求，`store:false`，不携带历史、会话 ID 或 `previous_response_id`。保持流式协议以覆盖 OAuth；只有终结完整的最终回答参与提取，推理和 commentary 不参与。不加入不通用的 temperature/seed 参数，不为追求简短把总推理输出预算设得过低。保持单轮 120 秒超时；高深度超时也归未知，界面提示可能需要更长耗时，本版不自动延长或切深度。

严格输出保证形状的前提是端点支持、响应完成且无拒答，不能保证数学答案正确。官方参考：[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)。核验日期为 2026-09-14；官方 API 文档不能证明任意订阅端点或转发上游的兼容性。

## 5. 提取与判分

把 `AnswerIs21(bool)` 调整为有明确结果的提取函数：返回规范化数值、来源、可靠性/原因；`Grade` 仅比较完整可靠的答案和标准答案。

处理顺序为 JSON 对象、完整纯数字、明确结论文字。JSON 使用严格完整解码，检测重复键、尾随对象、损坏结构和非法字段类型；一旦识别为损坏结构，不降级为正则从中抓取 21。兼容 `answer` 数值和纯数字字符串、单个 JSON 代码块；额外解释字段不凭中间数字改变 `answer`，明确矛盾则未知。数值用精确十进制/整数解析，不经过 `float64` 丢失精度。

文本优先提取明确的最终结论，屏蔽否定、引用、反例和不确定候选；不以全文最后一个数字或最后一个正则命中作为答案。明确更正可替代早先答案；多个互相冲突且没有明确更正的最终答案为未知。无法可靠识别的表达为未知，不宣称能理解所有自然语言。

| 完整最终回答 | 新状态/原因 |
| --- | --- |
| JSON 或数字 21，或明确结论为 21 的解释 | 聪明 / `correct_answer` |
| 明确最终数值不是 21，如 29、21.5 | 降智 / `wrong_answer` |
| 21 或 29、否定但不给答案、互相冲突 | 未知 / `ambiguous_answer` |
| 无答案、拒答、字段损坏/重复 | 未知 / `unparseable_answer`、`refusal`、`invalid_answer_structure` |
| 超时、断链、HTTP 错误、模型/参数不支持、流不完整、超限 | 未知 / 对应传输或协议原因 |

未知是有明确错误原因的检测失败，不代表聪明。本方案拟把部分旧版降智改为未知，这是行为变更，需要在后续发行说明中明确。

## 6. 状态、排期与并发

保留 `enabled && status == degraded` 的唯一 IQ 调度限制和单次判定语义。聪明/未知/关闭检测解除本模块限制；人工停用、调度开关、额度、过期与其他健康限制保持有效。正在处理的业务请求不打断，降智账号继续接受周期检测。

只修改间隔：保留状态和 revision；无运行任务时依据上轮完成时间重新计算到期时间，已过期则立即排队；有任务时其完成后采用最新间隔。保存完全相同的配置是幂等操作。

修改检测模型、深度、输出模式或人工修改身份、端点、协议、有效请求头及传输配置：在同一事务中更新配置/revision、将状态置未知并排队新配置；旧任务失效并不得覆盖新结果。保持旧租约至退出或到期，同账号不重叠。变更配置会解除旧配置的 IQ 限制，界面显示“配置已变更，等待检测”；这是旧结果不再适用的明确行为，不能隐式显示聪明。正常令牌轮换及单纯拉取模型列表不改变检测 revision。

每次领取任务固定配置快照，记录、实际请求和判分使用同一快照；提交仍检查 token/revision。模型与深度改变会改变测量条件，不对前后不同配置做连续通过计数。

保持跨实例总并发 10、扫描 15 秒、请求超时 120 秒和租约 180 秒。常规下次时间在完成后间隔基础上增加 0～min(30秒, 间隔的5%) 的持久化抖动，降低批量同刻触发；首次启用和“立即检测”不加抖动。队列按到期顺序公平领取。

不对完整的错误答案自动重试。后台因网络故障得到未知后等待下一正常周期；手动立即检测仍须任务去重。进程崩溃/租约过期的遗留轮次显式记未知、中断原因并清理对应 IQ 限制，再排队新轮，不能让旧降智状态因工作者失联永久挂住；与正常完成竞争时在同一账号锁内裁决。

## 7. 数据、接口和界面记录

`accounts.iq_check` 继续存配置与状态，扩展模型、深度、格式及有效配置版本。管理员 PUT、创建、编辑及批量更新支持可选新字段；列表精简 DTO 也携带它们，防止开关提交覆盖自定义值。接口参数 `reasoning_effort` 为 `upstream_default` 时数据库保留该选择，实际请求省略参数，记录显示“上游默认”。

`account_iq_check_results` 追加必要列：`normalized_answer`（可空精确字符串）、`answer_format`、`output_mode`、`format_compliant`、`grader_version`、`protocol`、`reported_model`（可空）、`config_revision`。沿用 `answer` 保存原始最终回答、`model`/`effort` 保存请求值；`reported_model` 仅说明上游报告值，不能据此证明真实执行模型。

插入记录时显式写 `prompt_version`、`grader_version`、`model`、`effort`、协议和 revision，不能依赖迁移 240 的默认常量。旧记录按其旧版本保留，不改写成 v2；新字段可空，前端将旧记录标记为旧版且仍显示原回答。取消/中断记录也能看到当时请求参数。

继续使用两轮原子保留：每次产生第三轮记录即删除最旧一轮；失败、取消和中断均计入。原始文本只存一次，不进入通用日志、缓存或另一个历史表。响应/答案上限维持 256 KiB / 64 KiB。

记录弹窗主要显示“提取答案：21 / 聪明 / 最终答案正确”，或“提取答案：29 / 降智 / 最终答案不等于21”；原始回答默认折叠，原样显示。展示本轮模型、深度、配置变更提示与安全的错误原因；运行中显示“检测中”，不以 0 ms 和未知伪装完成。绿色/黄色/灰色和原蓝色开关保持一致。

## 8. 文件范围与实施顺序

1. `backend/internal/pkg/iqcheck/`：配置化 Payload、统一提示、精确提取与流解析；先补复现用例。
2. `backend/internal/domain/iq_check.go`、`service/iq_check_service.go`、`repository/account_iq_check.go` 和 `account_repo.go`：默认兼容、快照、更新语义及记录。
3. `service/upstream_models.go` 及管理员 IQ 路由/处理器：无账号写入副作用的模型目录；复用认证和传输。
4. `backend/migrations/`：实施时选择下一个空闲编号，只追加；同步 Ent schema/生成代码，按依赖变化更新 Wire。现有迁移 240 不修改。
5. `frontend/src/components/account/IQCheckSettings.vue`、编辑/批量表单、类型/API、记录弹窗和中英文文案。
6. 按 tasks/spec 运行后端、数据库、前端和兼容验收，更新 `docs/OPENAI_IQ_CHECK.md` 与项目记忆。

发布时保证同一检测工作者版本，先排空旧任务再切换新检测器，避免 v1/v2 同时领取任务。迁移保留当前结果，不因升级批量启用检测；旧配置首次读取补默认。实施完成后单独执行版本与发布流程；回滚前保存检测配置，旧二进制忽略新配置的行为必须验证，不把源码回滚等同于生产数据库降级。

## 9. 稳定性的边界

本方案保证相同完整输入在同一判分版本下有确定结果、格式差异不改变答案21的判定、任务/配置不会串轮。模型自身仍可能在两次独立调用中答出不同数值；保持单次判定就会对应改变状态，不承诺状态永不切换。

GPT-6 Astra 默认仍用 `low`；官方模型文档列出的档位为 `low/medium/high/xhigh/max`，不把同一组档位套到所有自定义模型。参考：[GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra)，核验日期 2026-09-14。更高深度可能改变题目表现和耗时，记录必须能区分配置。
