# 设计：输出后失败尝试补记

## 确认、补记与归因

只有 HTTP 请求已向客户端送出可见内容，且既有快层实际计入账号失败，才记录补记事实。读流出错、缺终态和带内失败事件分别以 `stream_read_error`、`missing_terminal`、`stream_failed` 记为 `TRANSIENT`；出字后停滞以 `stall` 记为 `STALL`。元数据和心跳不算可见内容。客户端取消或上下文结束若先于快层确认，则不补记；快层确认后才取消（最终响应仍可能是 HTTP 200）仍照常补记。出字前停滞、请求级拒绝和未由快层计入的事件不补。已有鉴权、容量、限流、余额或客户端错误等事件时保留原类别，遵循 0.5.1 报错补漏的分类。

每次实际发送 HTTP 请求前按账号记录当前事件序号，含插件转发路径；原地重发也更新边界。失败事实保留发生时的边界；合并时仅检查边界后同账号事件，因此先前失败与最终断流可各记一次，同一次尝试不重复。带内失败已有直接登记（例如 `response.failed`）时同样按发送边界去重，保留直接登记事件。边界不可用时，只要请求中已有该账号事件便跳过补记，允许漏记以避免重复；不以毫秒时间窗或不随原地重发更新的尝试起点代替边界。

补项使用 `stream_failed`，记录账号快照、真实失败时刻、类别、原因与非空安全消息；带内失败使用 `upstream reported a failure after output`，其余原因保留原有消息，不写上游原文或虚构的上游 HTTP 状态。补项不是 `failover`，不再触发暂停、会话失败或回合失败，也不改变计费、最终状态码和对客错误帧。重复合并应保持幂等。

常规错误、带内终态错误和显式 HTTP 流错误均先把补项合入请求上游事件上下文，再分类并写入最终错误记录；显式 HTTP 流错误同样读取合并后的上下文。流错误快照只用于 WebSocket 回合，不含补项。有补项时沿用既有归因 `upstream / provider / upstream_http`；`upstream_http` 是来源分类，不代表实际收到 HTTP 5xx。带内终态顶层上游状态可能是逻辑状态，不作为补记依据。保留请求级错误分类、监控过滤、脱敏与队列上限。

WebSocket 回合与连接退出均不补记，回合间新增事实须隔离，原有快层状态不变。其他平台共用既有快层与运维边界，不扩判新类别。

## 读取方与发布

门槛多读到软失败，同请求同账号的用量行不再算成功，熔断和观察期再熔断可能增多；份额健康分母为用量条数加软失败条数，不做门槛的同请求扣重。阈值、计费、业务标志、严重级别、SLA 和总错误率口径不变。

上游错误率按 `provider` 且排除 429/529，归因修正可能增加该指标并触发已有告警，平台内部桶相应减少；管理端阶段和供应商列表、用户端错误分类也随之变化。渠道监控 V2 总错误请求数不变，上游受影响请求数和尝试数可能增加，部分 `internal` 转为 `upstream_5xx`，已命中 `timeout`、`transport_or_stream` 等优先类别的仍按原规则。该桶不证明实际收到上游 5xx。换号趋势不变。

仅新记录使用新口径，历史不回填；跨发布点的桶变化不能直接解释为质量变化。不新增配置或部署前提。
