# 输出后失败尝试补记

## ADDED Requirements

### Requirement: 确认后的 HTTP 失败补记

系统 MUST 仅为已向客户端输出可见内容、且快层实际计入账号失败的 HTTP 尝试补记缺失的上游事件。读流出错、缺终态分别使用 `stream_read_error`、`missing_terminal` 和 `TRANSIENT`；出字后停滞使用 `stall` 和 `STALL`；带内失败事件使用 `stream_failed`，类别 MUST 与同载荷直接登记采用相同的状态及类别规则，`RATE_LIMIT`、`CAPACITY_SHED` 等非软失败类别 MUST NOT 计入门槛或份额软失败。OpenAI 快层的会话失败、冷却与失败计数仍使用 `TRANSIENT`。开场元数据和心跳不算可见内容。对读流出错、缺终态与停滞，客户端取消或上下文结束若先于快层确认，则 MUST NOT 补记；快层确认失败后客户端才取消（最终响应仍可能为 HTTP 200）时 MUST 照常补记；客户端离开后若上游仍在读取并实际送达带内失败事件，MUST 照常补记，与直接登记的 `response.failed` 一致。请求级拒绝、出字前停滞或快层未计入的事件 MUST NOT 补记。

#### Scenario: 输出后读流中断

- **WHEN** HTTP 流送出内容后读流出错，快层确认账号失败，且本次发送后没有同账号事件
- **THEN** 运维记录包含一条 `stream_failed` 尝试，原因为 `stream_read_error`，类别为 `TRANSIENT`，带真实失败时刻和非空安全消息，不虚构上游状态。

#### Scenario: 输出后带内限流失败

- **WHEN** HTTP 流送出内容后收到带内限流失败事件，快层确认账号失败，且本次发送后没有同账号事件
- **THEN** 运维记录包含一条 `stream_failed` 尝试，原因为 `stream_failed`，类别为 `RATE_LIMIT`，不计入门槛或份额软失败。

#### Scenario: 输出后带内瞬时失败

- **WHEN** HTTP 流送出内容后收到带内瞬时失败事件，快层确认账号失败，且本次发送后没有同账号事件
- **THEN** 运维记录包含一条 `stream_failed` 尝试，原因为 `stream_failed`，类别为 `TRANSIENT`，消息为安全的带内失败提示，不含上游原文。

#### Scenario: 延迟确认的裸错误

- **WHEN** OAuth 类账号在输出后收到裸 `error`，快层等待终态或停滞条件后才确认失败
- **THEN** 补项的失败时刻为快层确认时刻，而非裸错误事件到达时刻。

#### Scenario: 客户端离开后收到带内失败

- **WHEN** 客户端在已有输出后离开，而上游读取继续并随后送达带内失败事件
- **THEN** 快层仍确认上游实际报告的失败，并补记该尝试。

#### Scenario: 带内失败已有直接登记

- **WHEN** 输出后带内失败已直接登记同账号事件（例如 `response.failed`），之后在写运维记录前合并失败事实
- **THEN** 按发送边界去重，保留直接登记的事件，不追加第二条。

#### Scenario: 同次尝试已有分类

- **WHEN** 本次发送后已有同账号的鉴权、容量、限流、余额或客户端错误等事件
- **THEN** 保留原事件和类别，不追加补项。

#### Scenario: 确认失败后客户端取消

- **WHEN** HTTP 流已输出内容，快层先确认失败，随后客户端取消，最终响应仍为 HTTP 200
- **THEN** 仍补记该失败尝试，且不改变最终状态码。

### Requirement: 按实际发送边界去重

系统 MUST 为每次 HTTP 发送建立按账号的事件边界，包括插件转发路径及同号原地重发；补记时只检查该边界之后的同账号事件。没有有效边界时，若本请求已有该账号的任何事件 MUST NOT 补记。重复信号或重复合并 MUST NOT 增加重复条目或重复惩罚。

#### Scenario: 同号重发

- **WHEN** 前次发送已有失败事件，同账号原地重发后输出内容并发生已确认的断流，即使两个动作发生在同一毫秒
- **THEN** 前次事件不阻止本次缺失尝试的补记。

#### Scenario: 无边界

- **WHEN** 无法取得有效发送边界且请求中已有该账号事件
- **THEN** 不补记，即使可能漏掉后续尝试。

### Requirement: 补记先于归因且不改变请求结果

系统 MUST 在常规、带内终态和显式 HTTP 流错误路径中先把补项写入请求上游事件上下文，再归因并写入最终记录；显式 HTTP 流错误同样读取合并后的上下文。流错误快照只用于 WebSocket 回合，不含补项。沿用既有 `upstream / provider / upstream_http` 分类；来源分类不代表实际收到上游 HTTP 状态。补项 MUST NOT 冒充 `failover`，也 MUST NOT 再次触发暂停、会话失败或回合失败，或改变计费、最终状态码、错误类型和对客错误帧。

#### Scenario: 缺失上游上下文的断流

- **WHEN** 已确认的输出后失败补入尝试
- **THEN** 错误归因于上游供应商，补项进入最终记录，业务标志和严重级别保持原有语义。

#### Scenario: WebSocket

- **WHEN** WebSocket 回合失败或连接退出
- **THEN** 不合并补项，回合间补记事实隔离，原有快层状态和归因不变。

### Requirement: 读取方口径

门槛 MUST 将补入的软失败纳入既有判定，对同请求同账号用量扣重；份额健康 MUST 保持用量条数加软失败条数的分母，不做该扣重。阈值不变。补项只影响新记录，不回填历史；SLA、总错误率与换号趋势口径不变，上游错误率、错误列表分类和渠道监控 V2 可随归因变化。

#### Scenario: 用量和补项同属一次请求

- **WHEN** 同请求同账号有一条用量和一条补入的软失败
- **THEN** 门槛计一次调用和一次软失败；份额健康按各自条数纳入分母。
