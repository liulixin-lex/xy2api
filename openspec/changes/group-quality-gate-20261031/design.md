# 设计

## 质量门槛配置

设置键 `group_quality_gate_policies` 按分组 ID 存策略，带 `version`，写入时比较版本，冲突返回 409。每组字段如下：

| 字段 | 含义 |
|---|---|
| `enabled` | 默认关闭；关闭时本组判定与现在完全一致 |
| `max_error_rate` | 错误率熔断线，默认 0.10，取值 (0, 1] |
| `max_warm_ttft_p90_ms` | 续轮首字 p90 熔断线，默认 20000 |
| `fast_warm_ttft_p90_ms` | 快档线，默认 10000，只用于排序，必须小于熔断线 |
| `pinned_account_ids` | 固定账号，必须是本组成员 |

- 只对 OpenAI 平台的分组生效。其他平台的分组不显示这个区块，接口也拒绝启用。
- 在分组编辑框里修改。不加迁移，不改 Ent。

## 指标

按账号算一份，所有分组共用。每 60 秒在只读事务里查一次，启动时立即查一次，请求路径不写统计。

- **错误率**（15 分钟）：软失败 ÷（成功 + 软失败）。
  - 成功取 `usage_logs`；软失败取 `ops_error_logs.upstream_errors` 中 resilience 分类为 TRANSIENT 的尝试（首字超时、5xx、断流、连接错误），以及未分类、无状态码、非取消的 `request_error`。
  - 按 `(request_id, account_id, at_unix_ms)` 去重。
  - 不计 429、余额、鉴权、请求错误、用户取消、容量削峰、模型不支持。
  - 总数 ≥20 且软失败 ≥5 才判定。
- **续轮首字 p90**（30 分钟）：流式成功请求，同 `(session_id, account_id)` 的上一条在 5 分钟内；样本 ≥10 才判定。首字超时只计入错误率。不按推理强度拆分。
- **续轮零缓存率**（2 小时）：续轮且提示 ≥2048 token 的请求中 `cache_read_tokens = 0` 的占比，样本 ≥20。不参与熔断，只用于排序：超过 30% 的账号不算快档。
- **有效数据**：每个“分组 × 账号”的判定只用以下时刻中最晚的那个之后的数据：
  - 窗口起点；
  - 重置时刻（`accounts.extra.group_quality_reset_at`）；
  - 该账号在本组最近一次熔断结束的时刻；
  - 本进程启动时刻。熔断结束时刻只在进程内，重启后不读旧样本，从启动起重新积累。
  熔断前的数据在熔断结束后不再计入，由试用重新验证。账号列表显示的仍是完整窗口的指标。

## 判定与状态

每分钟对每个“启用门槛的分组 × 成员”判定。状态有三种：合格、熔断、试用。

- **熔断**：错误率或续轮首字 p90 超过上限（各自满足样本要求）。
- **时长**：按连续次数 5 → 10 → 20 → 30 分钟封顶；连续 2 小时没再熔断，次数清零。
- **到期时**，只看熔断开始之后的数据（该账号在其他分组的流量也算，因为指标按账号计）：
  - 新数据足够且仍超线：进入下一档；
  - 新数据足够且回到上限的 80% 以内：合格；
  - 其他情况（新数据不够，或介于 80% 与 100% 之间）：试用。
- **试用**：正常参与调度，只看试用开始之后的数据。前 20 个请求内软失败 ≥2 次，或新数据满足熔断条件，就进入下一档熔断；满 20 个请求转合格。试用期的请求数与软失败数从试用开始逐分钟累加，不受 35 分钟取数范围限制，直到转合格或再熔断。
- 熔断期间账号在本组没有流量，窗口里只剩熔断前的旧数据。上面两条保证这些旧数据不会让已经恢复的账号被连续熔断。
- 熔断只作用于该分组的调度：不改 `schedulable`，不写 `temp_unschedulable`，不改 `account_groups`。
- 状态在进程内，用原子快照。重启后第一轮重算。多实例各自由同一份数据计算。
- 评估失败或数据超过 5 分钟没更新：沿用上一轮、不新增熔断，记 `group_quality_gate.evaluate_failed`；已有熔断照常到期。

## 保底、固定账号与可服务

评估器对每个“分组 × 成员”给出分层结果，各处按需取用，不合成一个布尔值：

| 概念 | 定义 | 用途 |
|---|---|---|
| 可用 | 平台匹配、启用、可调度、无硬状态（余额暂停、鉴权错误、长限流、错误状态）；本组开利润门时，成本不超过上限（按分组默认倍率与当前高峰估算）。不看软罚与质量门槛 | 保底分母 |
| 达标 | 指标未超线（合格或试用）。固定账号同样按真实指标算 | 保底分子 |
| 否决 | 处于熔断，且不是固定账号、不是保底保留 | 选号 |
| 可服务 | 可用、无软罚、未被否决 | 兜底触发、运维可用数与告警 |

- **判定时**：可用且“达标或保底保留”的成员数，不得少于 max(2, ⌈可用成员数 / 2⌉)。
  - 这个目标以“可计入成员”的数量为上限：可用、且不是“固定但不达标”的成员。达不到时，可计入成员全部保留可选。例如组里只有 1 个可用账号且超线，它被保底保留。
  - 不足时按超线程度从轻到重留下熔断账号，标“保底保留”，记 `guard_hold`。
  - 有兜底组的分组也一样。
- **请求时**：组内没有其他可选账号时，末位兜底放宽质量熔断。利润门、智商、余额、鉴权、模型不支持不放宽。
- **固定账号**：从不被否决。指标、状态、排序照常；利润门、智商、硬状态照常生效。不达标时算可服务，但不计入保底分子。

## 会话与手动干预

- **质量熔断时直接改绑**：资格函数返回 `group_quality_ejected`，现有粘性逻辑放弃原账号，由新选中的账号改写绑定。短时软罚与满载仍保留绑定、临时借用。
- **强续接豁免**：previous_response 与 guardian 父账号路径带显式豁免标志，DB 复核和 WS 每个 turn 的复核都识别它。
- **恢复状态**：
  - 只有管理端“恢复状态”（`POST /api/v1/admin/accounts/:id/recover-state`）写入 `accounts.extra.group_quality_reset_at`。`AccountRecoveryOptions` 为此新增一个显式选项，只在这个处理器里开启。
  - “测试”成功后的自动恢复与 OpenAI 额度重置流程也调用 `RecoverAccountState`，它们不写入。
  - 写入用 `UpdateExtra` 的 JSONB 合并，不影响其他 extra 字段。前面的清理完成后写入失败，就返回错误；重试是幂等的。
  - 下一轮评估清除该账号在所有分组的熔断，次数清零，转为试用。
- 不加新按钮。“测试”不影响门槛；整组暂停就关闭门槛。

## 调度接入

**装门**：范围与利润门完全相同（见 `openai_profit_control.go` 文件头的装门点清单）：
- 各文本入口在请求开始时装门；
- `selectAccountWithScheduler`，以及公开的 `SelectAccountWithLoadAwareness`、`SelectAccountByPreviousResponseID`，做防御性装门；
- WS 每个 turn 重新装门；
- 选号结果携带实际生效的分组（组合分组解析出的子分组），终检用它；
- 利润门豁免的路径同样不装门：独立图片与视频端点、媒体、count_tokens、live；
- 模型目录（`SelectAccountForModel*`，供 Codex 模型列表与 `/models` 使用）只读元数据，不装门。

**否决**，原因码统一为 `group_quality_ejected`：
- 候选过滤与调度器内的终检（`isAccountRequestCompatibleReason`）；
- legacy 资格判断与 DB 复核；
- 粘性命中；
- 份额调度：普通候选、缺绑定候选和最终校验；
- 处理器在抢槽或 WaitPlan 成功后的终检。

**终检否决后**：
- HTTP 请求：释放槽位，本请求排除该账号，重新选号。
- WS 首个 turn 使用建连选号与抢槽后的终检结果，不再重复复核；建连终检已经包含 previous_response、guardian 局部豁免与末位兜底放宽，避免固定续链或兜底账号在 turn 1 被关闭。
- WS 连接的后续 turn：被续链固定的 turn 豁免，判定与现有 OpenAI 质量路由相同（带 `previous_response_id`，或有未完成的工具调用）；其他 turn 关闭连接并要求客户端重连，连接内不换号。豁免能避免“重连后回到同一账号又被关闭”的循环。

改到的原版调度文件，登记具名补丁与 `scheduler-diff.json`。

## 排序与满载

- **档位**（只在“低倍率优先”开启时参与排序）：
  - 第 0 档：合格且快档。快档 = 续轮首字 p90 ≤ 本组快档线（无配置用 10000），并且续轮零缓存率不超过 30%（零缓存样本不足 20 时不看这一条）。首字无数据算快档；首字样本不足时沿用上次档位，最长 6 小时。
  - 第 1 档：试用中的账号，不看旧档位。合格的快档账号满了或不可用时，由它先接，这样它能重新拿到流量、证明自己已恢复。
  - 熔断结束时清除该账号在本组的档位记忆。转合格后按试用以来的数据定档；首字样本不足时按“无数据”算快档，不沿用熔断前的慢档。
  - 第 2 档：其他账号，包括慢档、零缓存超线、保底保留、固定但不达标。
  - 没开门槛的分组没有试用状态，只分第 0、2 档。
- **比较键**（低倍率优先开启时）：
  1. 档位；
  2. `Account.Priority`；
  3. 负载 ≥80% 的账号排后；
  4. 成本（`openAISchedulingRate`）；
  5. 负载；
  6. 最近使用；
  7. ID。
  - 第 3 项让新会话避开快满的账号，给已绑定的会话留出余量，减少满载借用。负载 = (在途 + 排队) ÷ 并发上限；没设并发上限、也没设负载系数的账号，这一项按中性处理，不算快满。
  - 低倍率优先关闭时，顺序与现在完全相同。
  - legacy 的全部排序点共用这一个比较器。E2 替补只在同一档位、成本、负载带内重排。
- **满载**：粘性账号抢不到槽位时：
  1. 在调度器里短间隔重试抢原账号的槽位，最多 2 秒，尊重请求取消。不进排队计数；抢到就只交付这一个槽位的释放函数。
  2. 仍然满，就在本次选号里排除原账号，借用本组一个空闲的合格账号，本次借用、不改绑定。
  3. 全组都没有即时空位，才对粘性账号生成最终的 WaitPlan（与现在相同）。原号粘性队列已满时，按 Layer 3 比较器在全池选择等待账号，使用 fallback 等待时限与上限，仍不改绑定；强续接只等原号。排队计数只为这个 WaitPlan 加减一次。处理器的 WaitPlan 超时语义不变。
  - 借用的账号按同会话稳定顺序选：先按比较键选出最优的一档，同档内优先这个会话最近成功用过的账号，否则按会话固定的哈希顺序。这个顺序从 E2 替补里抽出共用，三条满载路径（legacy 无 LoadBatch、负载感知、高级调度）都用它。借用时近期成功与稳定哈希先于负载带筛选，仍保持档位、优先级、成本与 compact 边界，并将判慢账号置后。高级调度的成本口径跟随其自身成本权重，不启用 legacy 低倍率开关。反复借用会落在同一个账号上，缓存能接上。
  - 强续接仍等原账号。
- **缓存**：上游缓存按账号计算，命中率主要取决于会话是否留在同一账号。
  - 排序变化只影响新会话，粘性会话不动。
  - 质量熔断时改绑一次，账号恢复后会话不回迁。
  - 满载先短等，借用落在固定账号上。

## 利润门

- **成本**：与排序同源，用 `openAISchedulingRate`。新鲜探测值含上游高峰，否则用 `rate_multiplier`；OAuth 账号用运行时参考倍率。
  - 先校验原始倍率：nil、负数、NaN、Inf 拒绝；0 是合法的免费倍率。
  - 时刻用 `pricingAt`，终检不用当前时间。
- **售价**：取计价分组，与计费同源。兜底时是兜底组，否则是 API Key 的分组（组合分组为父分组）。售价 = 用户覆盖倍率或分组倍率，乘该组高峰。
- **开关、毛利率、安全缓冲**：取被调度分组，兜底时即兜底组。
- 保底、可服务判定与预览不针对具体用户，都按分组默认倍率估算。
- **界面**：开启时毛利率默认 20%，安全缓冲不再显示、保存为 0。编辑时显示按当前时刻换算的上游倍率上限，以及“N 个可调度成员中 M 个能通过”，例如“相当于上游倍率 ≤ 0.176，11 个中 7 个通过”。M=0 红字并要求确认，M=1 黄字。
- 配置用利润率而不是上游倍率上限：改分组倍率或有分组高峰定价时，上限自动跟随，一个默认值适用所有分组；界面显示换算出的上限，同样直观。
- 挡光全组时不放行亏本，按兜底链路处理。

## 兜底分组

**链路**：中间件在认证之后、模型解析与选号之前执行。
1. 按组级判定原组是否可服务：存在可服务成员（计入利润门与质量熔断，不看模型）。
2. 原组可服务：留在原组选号，末位兜底只放宽质量熔断；仍无号返回“无可用账号”。
3. 原组不可服务、兜底组可服务：整个请求转到兜底组（WS 为整条连接），按兜底组的规则选号与计价。兜底组内无号时返回“无可用账号”，不再串联兜底。
4. 原组不可服务、没有可服务的兜底组：留在原组走末位兜底；仍无号返回“无可用账号”。

key 记忆、稳定 120 秒后回原组、每个请求最多兜底一次，都保持不变。

判定不看模型：原组有可服务账号，但都不支持所请求的模型，或该模型被智商检测停用时，不触发兜底。这与现状相同。组合分组的兜底判定也保持现状。

**两个身份**：请求同时带着原组与服务组。
- 原组：`BillingAPIKey`，只用于权限与限额。
- 服务组：中间件改写后的 Key 与分组，用于计价。新增 `ServingPricingKey` / `ServingPricingGroup` 表达它。
- 各价格点去掉“兜底时回退到原组”的分支，改取服务组：请求计价上下文、OpenAI 与通用两处利润门、渠道计费字段、各用量记录路径。

**规则与计价**：
- 在兜底组里，质量门槛状态、保底、固定、快档线、利润门全部按兜底组。
- 计价按兜底组：分组倍率、用户在兜底组的覆盖倍率、高峰、图片与视频价、长上下文、渠道定价与计费模型，以及兜底组的“强制 Fast / Fast 按标准价”规则。删除兜底专属的标准价补差。
- 权限与限额仍按原组：
  - 模型白名单与模型列表；
  - 图片与 /v1/messages 资格（资格按原组，能力按兜底组）；
  - 分组 RPM 与“用户 × 分组”计数；
  - API Key 额度与余额检查。
- 在途预留：对象与计数归原组，金额按兜底组估算。
- WS 每个 turn：同时固定原组的授权快照和兜底组的计价快照，并按服务分组 ID 刷新兜底组的利润门。

**用量与显示**：
- 用量行：
  - `group_id` 为兜底组，`origin_group_id` 为原组；
  - `rate_multiplier`、`actual_cost`，以及图片、视频的金额字段，都按兜底组；
  - 账号侧成本与 `account_rate_multiplier` 不变；
  - 额度与余额的扣减对象仍是原 Key 和用户，金额按兜底组计价。
- 用户侧：分组显示原组，倍率与扣费如实显示，不出现兜底组名称。
- 管理端：分组标签显示原组，下方黄色显示“兜底 → 兜底组”，浮窗说明“按兜底分组计费”。筛选、统计、导出仍按服务分组。

## 可用数、告警与界面

- 运维“分组可用账号数”改为可服务成员数，`group_available_accounts` 告警随之变化，复用现有邮件告警。固定但不达标的账号计入可用数（它能接请求），但不计入保底。
- 账号列表：分组标签按状态着色（合格 / 熔断至 hh:mm / 试用 / 保底保留 / 固定）；悬停显示原因、实测值、上限、余量；行内显示三项指标，零缓存率超过 30% 标红。
- 分组列表新增“门槛：合格 n / 熔断 m”。
- 分组编辑框新增门槛区块与固定账号多选，只对 OpenAI 分组显示；快档线旁注明“低倍率优先开启时用于排序”。

## 接口与观测

**接口**：
- `GET /api/v1/admin/group-quality-gate/policies`
- `PUT /api/v1/admin/group-quality-gate/policies/:group_id`（带 `expected_version`）
- `GET /api/v1/admin/group-quality-gate/status`
- `GET /api/v1/admin/groups/:id/profit-control-preview`（返回成员数、可调度数、通过数与换算上限）

读接口跟随账号管理权限，策略写入与预览跟随分组管理权限，写操作进审计。

**日志事件**：`group_quality_gate.eject`、`.trial`、`.recover`、`.guard_hold`、`.last_resort`、`.evaluate_failed`。

## 升级与回退

- **升级即生效**：兜底计费改回兜底组、粘性满载借用、管理端用量显示、可用数口径。门槛和利润门都关闭时，可用数与现在相同。没有新的部署前提（反向代理、环境变量），`deploy/` 不用改；这些变化写进发布说明与现行文档。
- **用户配置**：门槛、利润门、低倍率优先、成员关系、并发上限都由用户升级后在界面上配置。不做分批上线、观察期、影子模式。
- **回退**：关闭分组门槛或利润门即回到原样，无数据残留；兜底计费只能随版本回退。

## 不做

- 零缓存门槛、分组级智商要求、全局冻结、同站点联动、按模型拆分门槛状态；
- 非 OpenAI 平台的质量门槛；
- 按模型判定兜底（改成“选号失败后再兜底”要改动所有协议入口）；
- 保本放行或紧急亏本开关；
- 自动改写成员关系、档位、建议模式、事件表、Redis 状态、主动探针、请求路径计数；
- 并发与站点上限的代码。
