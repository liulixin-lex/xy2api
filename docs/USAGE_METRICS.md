# 用量指标口径

适用于本次同步 Sub2API v0.2.15 后的用量明细、Token 趋势和运维页面。指标基于已记录的用量与耗时，不根据页面刷新速度或流式文本长度估算。设置键保留 `admin_usage_cache_hit_rate_enabled` 与 `admin_usage_token_speed_enabled`，避免升级丢失原有开关状态；谁能看到这两项见“显示与公开”。

## 平均TPS

使用记录的“延迟”列显示 **平均TPS**，单位 **t/s**（每秒输出 Token 数）。0.4.4 及以前叫“平均输出速率”、单位写 tokens/s，口径相同；运维页的单次请求速率仍叫“平均输出速率”，单位 tokens/s。

```text
单次请求平均TPS = output_tokens × 1000 / duration_ms
```

`duration_ms` 是该用量记录的完整请求耗时，包含首 Token 等待。流式与非流式使用相同公式。比如输出 100 Token、总耗时 3000 ms、首 Token 耗时 1000 ms，结果为 33.3 t/s；缺少首 Token 时间时仍是 33.3 t/s。

不能把完整输出数量除以 `duration_ms - first_token_ms` 后称为统一的输出速率：输出可能包含首个可见 Token 前的推理 Token，也可能直到结束才返回缓冲的工具输出。缺少首 Token 数据时退回总耗时会让同名指标混用两种口径。现有记录没有可靠的逐 Token 生成时间，不能据此计算模型纯解码速度。

用量明细仅展示适用的 Token 请求，排除图片输出、视频、非 Token 计费和 Live/未知请求类型；旧记录缺少请求类型或计费模式时仍允许按已有 Token 数据计算。输出或耗时不是有限正数时显示 `—`，不伪造 0 t/s。输出计数已经可能包含推理 Token，不再额外相加。显示开关继续生效（见“显示与公开”），不因上游组件更新而绕过设置。

`first_token_ms` 与 `duration_ms` 都从最后一次（成功的）上游尝试开始计时，不含此前失败的尝试与换号等待；换过号的请求，客户端实际等待更长，各次尝试见运维错误记录的 `upstream_errors`。OpenAI 首字口径由设置 `openai_ttft_mode` 决定：`semantic`（缺省）把中转插入的伪保活帧也记为首个事件，与 0.3.0 一致；`visible` 只算真实输出（见 [网关韧性](GATEWAY_RESILIENCE.md) §3）。

运维中的 P5/P10/P50 是筛选范围内各条有效记录速率的分位数，Avg 是这些单次速率的算术平均；不把小时分位数平均成整个窗口的分位数。它们与全站吞吐量含义不同，样本仍沿用运维后端的筛选契约；明细额外保留本地的非 Token 计费排除规则。

## 缓存读取占比

用量日志记录的是 **计费用量**，页面使用 **缓存读取占比**，不将它描述为上游真实缓存命中率：

```text
缓存读取占比 = cache_read_tokens
             / (input_tokens + cache_creation_tokens + cache_read_tokens) × 100%
```

持久化的三类输入 Token 是互斥桶：

| 字段 | 含义 |
| --- | --- |
| `input_tokens` | 未缓存输入 |
| `cache_creation_tokens` | 缓存创建 |
| `cache_read_tokens` | 缓存读取 |

OpenAI 原始总输入含缓存明细，在 `backend/internal/service/openai_gateway_usage.go` 的 `RecordUsage` 中先减去缓存读取与创建再写入 `input_tokens`；Anthropic 的输入本来就不含缓存桶。不要在展示层再扣一次缓存，也不要将 `cache_creation_5m_tokens`/`cache_creation_1h_tokens` 再加到已经包含它们的创建总量上。

强制缓存计费会在 `backend/internal/service/gateway_usage_billing.go` 中将普通输入转为缓存读取，然后写入日志。因此这组持久化计数无法还原强制计费前的真实上游命中情况，也不能当作请求命中次数占比。没有有效输入（分母为 0）、字段缺失、负数或非有限值时，用量明细显示 `—`，Token 趋势保留断点；有输入但没有缓存读取时才显示 0.0%。

趋势和区间统计先累加三类 Token，再使用同一公式，不能平均各请求的百分比。例如一个 100 Token 全命中请求与一个 900 Token 未命中请求，区间占比是 10%，不是 50%。现有 `usage_log_repo_trend.go` 和 `channel_monitor_v2_repo.go` 已按桶累加，无需改写历史数据或迁移。

渠道监控的用户 API 会隐藏分子、分母等绝对流量；现有契约对无有效输入返回数值 0。该页面不能通过已隐藏的分母区分“无输入”和“有输入但未读取缓存”，本次仅统一其指标名称与说明，未更改此 API 或推测隐藏样本量。

## 显示与公开

系统设置“功能开关 → 管理员使用记录”控制上面两项指标，只影响显示，不影响统计与计费。每项指标两个控件，各项互相独立：

- 显示开关 `admin_usage_cache_hit_rate_enabled`、`admin_usage_token_speed_enabled`，缺省打开。关闭后，这项对管理员和普通用户都不显示。
- 开关左边的公开按钮 `usage_cache_hit_rate_public`、`usage_token_speed_public`，缺省关闭，即“仅管理员可见”；打开后为“公开”，普通用户的使用记录也显示这项。

公开设置（`GET /api/v1/settings/public` 与页面注入的配置）只给出生效结果 `user_usage_cache_hit_rate_enabled`、`user_usage_token_speed_enabled`：显示开关与公开按钮都打开才为 true，不暴露上面四个键。普通用户的使用记录页据此显示；管理员自己的“我的账户 → 使用记录”也属于用户页面，同样按公开状态显示。用户接口本来就返回计算所需的 Token 与耗时，公开只决定页面是否展示，不是数据权限控制。保存后，管理员当前页面立即刷新公开设置，其他用户在页面重新加载后生效。

## Token 吞吐量

渠道监控和运维流量卡的 **Token 吞吐量（tokens/s）** 是统计窗口内全部计费 Token 除以窗口秒数，包含输入、输出、缓存创建及缓存读取。它随请求并发量变化，不能与单次请求平均TPS直接比较。渠道监控的 `TPM ÷ 60` 与上述窗口计算等价。

## 账号列表的近期首字与错误请求数

账号管理“状态”列在状态徽标下方显示该账号**最近 3 分钟的首字平均**：取这段时间内该账号成功请求的 `first_token_ms` 平均值（口径见上文），没有样本时不显示；颜色沿用用量明细“延迟”列的分档（10/30/60 秒）。徽标右边的红色数字是**最近 10 分钟的错误请求数**，与“使用记录 → 错误请求”页筛选该账号后的条数同一口径（同一查询条件，只计客户可见的错误，不计已恢复的上游记录）；为 0 时不显示，点击在新标签页打开该页并自动筛选该账号。请求在某账号失败、换号后成功时不算错误请求，该账号不计数；运维监控关闭时不会产生错误记录。数据来自 `POST /api/v1/admin/accounts/recent-health/batch`，按当前页账号批量查询，缓存 10 秒。

“首字”下面还会显示该账号**最近 30 分钟的缓存读取占比**，使用与上文相同的公式：先分别汇总 `input_tokens`、`cache_creation_tokens`、`cache_read_tokens`，再计算缓存读取 ÷（输入 + 缓存写入 + 缓存读取）。30 分钟内没有输入（分母为 0）时隐藏这一行；有输入但没有缓存读取时显示 0.0%。悬浮提示中的请求数是该窗口内的用量记录数。批量响应通过 `cache_window_seconds` 声明 1800 秒窗口；统计与首字平均共用一次 30 分钟的 `usage_logs` 扫描，首字平均仍只使用近 3 分钟的样本。

## 容量列的分组并发

账号列表和分组列表的容量列可显示“当前并发 / 总并发 / 本分组并发”。绿色的第三个数表示这些账号当前正在处理、且归属于该分组的请求槽位数；账号如果同时属于多个分组，各分组显示各自归属的数量，而“当前并发”仍显示账号全部分组共享的实际槽位数。第三个数按账号逐个截断到当前并发，因此不会超过第一个数。账号并发上限为 0（不限制）的账号没有槽位记录，第三个数始终为 0。

归属依据是账号从哪个调度分组中选出：槽位成员沿用现有并发 Redis 有序集合，只在成员末尾带上 `|g<groupID>`；管理页读取后缀汇总普通槽位和 Live 租约，不增加请求路径上的 Redis 写入。账号页只有筛选一个具体分组时才显示第三个数；“全部分组”和“未分配分组”仍显示两个数。分组页对每个分组都显示第三个数。读取失败时采用空计数显示 0，不影响请求处理和选号。

已知局限：处理器中的等待路径使用 API Key 分组，而非调度时解析后的实际分组；Claude Code 专用回退分组或无效请求回退分组下，若槽位在这些等待路径中占用，可能记到原分组，因此会少算而不会多算。智商检测和 Codex ticket 的后台探测没有分组归属，不计入任何分组。蓝绿切换期间，旧进程写入的无后缀槽位仍计入账号总并发，但不会计入绿色数，待旧进程排空后恢复完整统计。

此功能不更改选号、路由、并发上限或计费，也不新增 Redis key 或写操作。可以安全回滚：无需数据迁移或清理，旧版仍会把带后缀的成员作为普通槽位计数，按进程前缀清理的逻辑也保持兼容；回滚期间分组页暂不提供绿色数。

## 运维看板的 SLA

运维看板的“SLA（排除业务限制）”只计状态码 ≥400、且没有标为业务限制的错误请求。业务限制是用户自身条件或本地策略导致的失败：余额与额度、订阅、用户并发与 RPM 限制、Key 鉴权与 IP 限制、分组策略，以及本地模型配置（分组模型白名单、账号模型映射）。

0.4.9（未发布）起，选号阶段找不到可用账号的失败（无号 503，运维记录阶段 `routing`）计入 SLA，不再标为业务限制；组内没有账号支持所请求模型时同样计入。上面列出的业务限制不变。只影响升级后写入的记录，历史记录不重新分类。按生产 48 小时数据，看板 SLA 会因此下降约 1.5 个百分点，这是口径修正，不代表服务变差。
