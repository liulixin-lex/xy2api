# Claude 缓存缺失补齐

本功能默认关闭。升级不会自动启用，也不发送能力探测或预热请求。

在管理后台「设置 → 网关」的「Claude 缓存补齐」中，先选择分组、调用 Key、组内原生 Anthropic API Key 账号，再核对完整上游地址及账号映射后的精确模型名。首次启用建议限定一个 Key。保存会校验资源归属和地址，不调用模型。

仅原生 `/v1/messages` 转发到明确匹配规则的账号时生效。请求原始的顶层、system 块、tools 定义或 messages 内容块只要存在 `cache_control`（包括 null、非法值），就不会补齐；工具参数或 schema 中的同名属性不是缓存声明。完成现有转换及分组 system 注入后，再检查一次已有声明，缺失时仅追加：

```json
{"cache_control":{"type":"ephemeral"}}
```

省略 TTL 表示默认 5 分钟。补齐只属于当前账号的发送正文，不改变共用请求或其他账号尝试。透传账号、OAuth/SetupToken、Vertex、Bedrock、Antigravity、OpenAI 协议转换和 count_tokens 不在范围内。请求开始时冻结可用规则；在途启用不会增加已预留请求的成本，关闭会在后续发送检查中生效。分组 fallback 不继承原分组的缓存授权。

## 支持与费用

Anthropic 的协议声明不代表任意兼容网关都支持。启用前，应对同一个完整地址、账号及最终模型核验冷写、重复热读、追加对话、关闭对照，检查真实 `cache_creation_input_tokens`、`cache_read_input_tokens` 及 5m/1h 明细。没有明细或明细矛盾时，不应宣布支持验收通过。上游拒绝字段时按原错误流程处理，本功能不会去掉字段重新收费调用。

首次冷写可能比普通输入更贵，重复使用才可能节省。余额预留在现有 token 估算、上限及倍率规则下，取普通输入和配置的 5m 写入价格较高者，并保守考虑规则内候选最终模型；这可能暂时多占用可用余额，实际结算仍完全使用上游 usage 和现有价格表。预留不是保证 token 数量准确的报价，也不是实际扣款。未匹配账号也可能经历保守预留，但不会因此增加结算金额。

既有 ForceCacheBilling 和 TTL 计费覆写仍按原设置执行；本功能不启用这些策略。数值诊断日志区分上游原始 usage、结算 usage、覆写来源和结算结果，不记录对话正文或凭据。XY2API 用量与扣费可自行对账；NewAPI 向终端用户的扣费、供应商账单需要分别取得记录，不能由本功能验证。

## 停用与回滚

直接关闭开关并保存。本实例立即更新，其他实例最长约 60 秒刷新；读取过期配置失败时停止补齐。已经发出的上游请求仍正常结算。资源被移除或换组后仍允许关闭保存；启用保存需重新通过归属校验。

配置存于既有 settings 表的 `claude_cache_fallback_policy`，没有新数据库迁移。回退旧版本前关闭并确认实例刷新；旧版本忽略该设置。

没有声明只是低命中的一个可能原因。前缀变化、请求间隔、最小缓存长度、路由账号变化及上游支持情况仍会影响命中；本功能不能替代真实请求归因。
