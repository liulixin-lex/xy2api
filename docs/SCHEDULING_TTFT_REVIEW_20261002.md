# 调度与首字复审（2026-10-02）

状态：本机 `8093` 测试站问题的实施记录；发布判断以修复后的实测门禁为准。候选起点为 `d3699dfd5`，测试站当时运行的业务镜像来自 `291ce0cba`。本轮只读测试库，不在文档中保存提示词、凭据或响应正文。

## 现场事实和根因

- 组 2 策略 v12：原生交付和恢复均开启，首输出窗 30 秒、总等待 60 秒、最多 3 次生成尝试。首事件约 1.7-2.6 秒的三条成功请求，首内容分别约 15.3、22.7、24.4 秒。17 次尝试的数据库 dispatch→MarkSent 准备埋点为 4.883–7.716 毫秒；sent_at 不代表 socket 发送完成，历史数据也不足以还原完整进入→发送耗时。不能把它冒称整个调度阶段的 p95。首协议事件与首内容之间的等待主要发生在上游。
- 多条失败尝试已收到首协议事件（约 2-3.7 秒），但 30 秒后以 `content_timeout` 取消，再换账号。测试站同时记录独立的供应商 502/503；严格优先级、已试账号和尝试预算耗尽时，真实不可用账号无法通过更快的路由算法变成可用。
- `Delivery && Recovery && ReplaySafe` 把普通请求也送入首答案暂存。`created`、`in_progress` 和推理事件在答案前被扣留；长推理还会耗尽首答案窗或暂存容量。这违背完整协议事件及时交付，也使已开始的上游生成被当作未提交重试，有重复执行与费用风险。
- 出站正文在最终模型故障门和分发阶段被完整扫描两次。10 MiB JSON 的单次扫描本机隔离基准约 26.3 毫秒，二次扫描给长上下文添加可避免的 CPU 延迟。
- 资格预检依次访问 PG 活跃数、Redis 并发、PG 账号/故障状态；尾延迟和任一共享状态错误会直接进入请求首事件时间或返回失败。必须保留选中账号发送前的权威资格和容量锁，预检优化不能改成使用陈旧状态越权发送。

## 固定参考与取舍

- new-api `1a4166d8e8ba9802d2ca56fe8ecf0ed5404e80d5`：内存渠道过滤、优先级排序和同层权重选择位于 `model/channel_cache.go`；启动重试与发送在 `controller/relay.go` 分开。其按重试索引切优先级层不满足本项目“同层先耗尽”，不能照搬。
- CLIProxyAPI `e2bff0107bb307337aaa19018ccddd55f64253d5`：`sdk/cliproxy/auth/selector.go` 先过滤停用/冷却，再在最高可用层使用 SWRR；`conductor_execution.go` 排除已试账号；`conductor_stream.go` 在首完整 payload 前处理启动失败，随后直接转发。其可选前导缓存默认关闭，配置明确提示缓存会显著增加可见延迟。WS 已发送创建消息后的执行未知状态须比参考实现更保守。

## 执行模型

1. 创建请求固定策略快照、所有权和统一 Ledger。硬资格过滤后，只从当前最高可用优先级用已有 SWRR 选账号。当前层的合格账号因尝试、容量或冷却耗尽后才能下一层；最终 `BeginDispatch` 原子占槽，竞争失败释放选号预留并重选。已有响应/工具所有者固定原账号。
2. 将连接建立、确定未发送、发送后状态未知、上游已响应、对外已提交分开记账。只有首上游身份/完整事件尚未交付、错误已分类且重放安全时，协调器才能用原 Ledger 重试；创建消息已发但结果未知不得伪装成恢复。身份或首事件交付前原子设置 `attemptCommitted`，此后仅同响应原生续传或准确流内终态。
3. 原生 SSE/WS 完整事件按原顺序逐个 `Write + Flush`，不按“是否回答文字”缓存。`semanticSeen` 和首答案时间只是指标；等待首事件、内容空闲、请求总截止分别计时。已有事件后的正常长推理不能触发首答案重生成。心跳不算首内容，也不修改提交身份。
4. 出站正文的最终模型/流式元数据在一次验证后随本次不可变请求携带，供最终故障门和分发复用；若适配器真正重写正文，必须重建快照。候选预检可减少不可能赢的层和重复读取，但所有选中账号仍需权威准入与容量锁。
5. 失败分类保留本地网络、客户端取消、供应商协议失败、容量/冷却与总预算的区别。供应商 502/503 可以在未提交且预算内降级；提交后绝不跨账号拼接。失败率与首内容分别按账号、优先级、模型和上下文桶观测，不自动改变管理员优先级/权重。

## 验收与上线边界

- 用同一 SSE/WS 输入验证 `created` 约 0.2 秒、内容约 5 秒、终态约 20 秒分别到达；含长推理、工具参数、未知事件及终态错误。首帧写入/超时竞态不能混流；断连、停止、账单及严格优先级/SWRR/容量用真实存储回归。
- 以短/长正文分别测量进入、选号、发出、响应头、首协议事件、首内容及 Flush。网关完整事件至 Flush 的既有目标 p95 <= 10 ms、p99 <= 30 ms；单次 10 MiB 准备的重复扫描必须消失。相同回放比较基线、修改及回滚，拒绝空匹配或跳过。
- 本机测试站先构建、排空替换和小并发验收，再扩大到 1/2/4/8/16。真实供应商内容时间、严格优先级下高层慢账号、供应商 502/503 均不是网关能够保证消除的延迟或失败。原生 WS 同响应续接、持久化/跨实例恢复仍未认证；不以本轮修复声明完整 v1.0 规范上线。

## 本轮审查补修

- 首事件停表仅作用于实际流式协议（semanticObservable）；非流式原生后台 queued 确认不解除原内容/客户端截止。真实 PostgreSQL 回归曾发现该边界错误，修复后六类后台收尾场景和流式启动门禁均通过。
- Responses/WS 的裸 [DONE]、缺失或非字符串 type 不作为有效启动证据；合法未知 type 继续原样交付。created 后的 EOF、超长事件、无效 JSON、读错误及空完成按原身份发送准确失败；已交付裸错误不重复合成终态。
- 透传 StreamDataIntervalTimeout 现在作用于实际上游读进展：网络分片计作读取，下游心跳和慢写不伪装成上游进展；保持现有默认值，不使用 30 秒首答案阈值中断正常推理。
- 工作流增加本轮 13 项必需测试并同步两个更名用例；零匹配或关键 SKIP 仍阻断发布。
- 同输入三态已观察到旧版和回滚版的 created/推理被暂存，修改版在答案被测试闸门阻塞时已真实 Flush。这是协议交付证据，不等同供应商答案时间保证；实测性能及测试站部署以外部 ttft-review-20261002 账本为准。
